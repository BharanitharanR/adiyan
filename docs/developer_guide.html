Building a new Adiyan agent

This is the guide for someone adding a new agent to the mesh: how to create it, which files are actually yours to edit, how to reach the platform's built-in capabilities (WhatsApp, the LLM, memory, your own storage), and exactly what permission to add for each one.

1. Create the agent

One command, run from the repo root:

python3 -m mesh.tools.bootstrap_agent weather_agent

This copies mesh/example_agent/, renames its identity (directory, AGENT_ID, class prefix, display name) into mesh/weather_agent/, and picks a free port for you (see §3). No terminal handy? The same thing runs in-browser from the public site's Create an Agent page — same zip, generated on your own machine either way.

It still has the reference roll_dice skill in it. That's your actual logic to write — nothing here should guess at it for you.

2. Files you'll actually touch

FileWhat it's for

skills_catalog.pyThe description text the Orchestrator's classifier reads to decide which agent handles which message. Written well, this is the only "routing config" you need.
seed_config.jsonDefault prompt templates and constants, seeded into Mongo on first boot (§9).
runtime_config.jsonDefault {model, temperature, ...} per LLM-calling stage (§6).

mesh/lib/permissions_config.jsonNot in your agent's own directory — a shared file. Add your tier here (§4).

3. Port & service registration

Port

bootstrap_agent assigns this automatically — it scans every existing agent's constants.py for a PORT = line, picks the next free number starting at 8440, and confirms nothing is actually bound to it on your machine. You don't choose it by hand.

Registering with the mesh (so other agents can find you)

This is automatic too, and needs no code from you: every agent's server.py calls mesh.lib.bootstrap.serve(), which calls mesh/lib/registry_client.py's register() for you at startup — posting your agent id and URL to Agent Registry (mcp.agent_registry.register_agent). Using the shared serve() boilerplate is "implementing the interface" — there's no separate registration step to remember.

Running it under start_all.sh

bootstrap_agent doesn't add your agent to mesh/start_all.sh's managed COMPONENTS list — you can run it standalone (python3 -m mesh.weather_agent.server) for development. To have start_all.sh start/stop manage it alongside everything else, add one line to that file's COMPONENTS array: 

"weather_agent|8441|mesh.weather_agent.server"

name|port|module — the same shape every other entry in that array already uses.

4. How the permission engine works

Every call — agent-to-agent, or into an MCP tool — carries a signed token with two claims: sub (who's calling) and tier (what they're allowed to do). The whole check is one function: 

is_allowed(claims, permission_key) -> bool
  # true if '*' is in the token's tier, or permission_key is listed in it
Call typeKey shapeExample
Calling another agent's skill<agent_id>.<skill_id>memory.search_knowledge_base
Calling an MCP toolmcp.<server_name>.<tool_name>mcp.whatsapp.send_message

Two directions to keep straight:

  1. To call someone else, your tier needs their key in its allow list.
  2. For someone else to call you, their tier needs your skill's key (<your_agent_id>.<your_skill_id>) in its own allow list — not something you configure on your own tier at all.

Add your own tier to mesh/lib/permissions_config.json, named <agent_id>_service by convention:

"weather_agent_service": {
  "description": "weather_agent's own outbound calls - state exactly why it needs each key.",
  "allow": [
    "mcp.whatsapp.get_own_phone",
    "mcp.whatsapp.send_message"
  ]
}

Then mint against it wherever you call out: permissions.mint_token('weather_agent', 'weather_agent_service'). List only what you actually call — a tier with one extra key is a tier that can do one more thing than anyone meant it to.

6. Calling the underlying LLM

No permission key for this either — every agent talks to the same local Ollama instance directly. The pattern every real skill in this mesh already follows (from mesh/journal/skills/craft_reflection_prompt.py): 

from langchain_ollama import ChatOllama
from pydantic import BaseModel
from mesh.lib import config_sdk

class MyResult(BaseModel):
    answer: str

async def run(...):
    cfg = await config_sdk.get_stage_config(
        AGENT_ID, 'my_stage', {'model': 'qwen3:8b-16k', 'temperature': 0.4},
    )
    model = ChatOllama(
        model=cfg['model'], base_url='http://localhost:11434', temperature=cfg['temperature'],
    ).with_structured_output(MyResult)
    result = await model.ainvoke(prompt)
    return result.answer

get_stage_config is what makes the model/temperature dashboard-editable later without touching code — see §9 for where its default (runtime_config.json) lives.

7. Memory: long-term vs. short-term

Both live behind Memory Agent, called the same way as any other agent (via call_agent) — the distinction is which skill:

SkillWhat it actually is
Long-term — the knowledge basesearch_knowledge_baseUploaded documents (PDFs, notes, ID cards) — global, not scoped to one person. Any fact that could plausibly be sitting in a document.
share_knowledge_documentSends back the original file, not just a snippet.
Short-term — conversation memoryrecall_contact_memoryActual back-and-forth chat history with one specific person — moods, goals, things they told the agent directly. A raw read-back, not a fact lookup.
remember_interactionWrites a new entry to that same per-contact history.
from mesh.lib.a2a_client import call_agent
from mesh.lib import permissions

token = permissions.mint_token(AGENT_ID, f'{AGENT_ID}_service')
result = await call_agent(MEMORY_AGENT_URL, 'search_knowledge_base', {'query': text}, token=token)

Requires memory.search_knowledge_base (or whichever skill you call) in your own tier's allow list — see §5.

8. Your own database

No permission needed — this is local filesystem storage, not a gated call. mesh/lib/paths.py gives every agent the same conventions:

FunctionFor
state_db_path(AGENT_ID)Your agent's own domain data (SQLite) — jobs, relationships, whatever your logic actually tracks.
tasks_db_path(AGENT_ID)A2A's own task-lifecycle bookkeeping — bootstrap.py's serve() wires this up for you already.
embeddings_path(AGENT_ID)Per-invocation embeddings, if your agent grows its own experience store over time.
kb_documents_dir(AGENT_ID)Raw ingested source documents, alongside their chunked/embedded form elsewhere.

Everything lands under ~/.Adiyan/agents/<agent_id>/ — generated, per-install, never checked into git.

from mesh.lib.paths import state_db_path
import sqlite3
conn = sqlite3.connect(state_db_path(AGENT_ID))

9. Configuring your own prompts

seed_config.json holds your defaults, each with a value and a human-readable description:

{
  "my_prompt_template": {
    "value": "Write a short reply about: {topic}",
    "description": "What this prompt is for, shown in the config dashboard."
  }
}

Every key in that file is seeded into Mongo automatically at startup (config_sdk.seed_from_file, already called from the template's server.py) — that's what makes it editable from the config dashboard afterward, without ever touching this file again. Read it live, anywhere in your code: 

value = await config_sdk.get_constant(
    AGENT_ID, 'my_prompt_template', seeded_default, description=seeded_description,
)

runtime_config.json is the same idea, specifically for {model, temperature, ...} stage configs — read with get_stage_config instead (§6).

10. Reaching WhatsApp

One class, from mesh/lib/agent_sdk.py:

from mesh.lib.agent_sdk import AdiyanAgent

agent = AdiyanAgent('weather_agent')
await agent.notify_owner("Rain expected this afternoon.")

notify_owner derives your <agent_id>_service tier, mints the token, resolves the owner's own phone, and sends — all internal. Returns False on any failure (never raises), matching this mesh's rule that a failed notification disappears quietly. The only manual step is the tier entry from §4.

11. Don't construct OpenWAService yourself

Known gap in this codebase today mesh/lib/utilities/whatsapp/openwa_service.py's OpenWAService talks straight to OpenWA's REST API with the raw vault key — no token, no tier, no permission check at all. Three call sites already do this instead of going through whatsapp_mcp (mesh/scheduler/skills/run_routine.py, mesh/adiyan_reader/skills/read_next_page.py, mesh/adiyan_reader/skills/dispatch_questions.py) — each one can send a WhatsApp message regardless of what any tier says. Don't build a fourth instance of it. Use AdiyanAgent (§10) instead — it's the same destination, through the one path that's actually checked.
