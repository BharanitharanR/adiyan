How permissions work, and how to add a new agent's

Every A2A skill call and every MCP tool call in this mesh goes through the same one-line question: does the caller's token allow this exact key? This guide is the reference for that system — how it works today, how to grant a new agent what it needs, and how to reach WhatsApp without touching any of the plumbing directly.

1. Tokens & tiers 2. How a call is checked 3. Tier reference 4. Adding a tier 5. Reaching WhatsApp 6. The bypass pitfall 7. Checklist

1. Tokens & tiers

Defined in mesh/lib/permissions.py, config in mesh/lib/permissions_config.json.

A token is a short-lived signed JWT (1 hour TTL) carrying two claims: sub (who's calling — a WhatsApp chat_id, or an internal agent id like "scheduler") and tier (what they're allowed to do). Minted once, right when identity is actually known, then carried on every downstream call — an A2A call's metadata, or an MCP tool's Authorization header. 

from mesh.lib import permissions

token = permissions.mint_token(subject='scheduler', tier='service')

A tier is just a named entry in permissions_config.json with an allow list of permission keys. Nothing else defines what a caller can do — no per-agent hardcoding, no special-casing by sub. The token's tier claim is the entire decision.

2. How a call is actually checked

Every check reduces to one function:

is_allowed(claims, permission_key) -> bool
  # '*' in tier's allow list, or permission_key in it. That's the whole rule.

The permission_key shape depends on what's being called:

Call typeKey shapeExample
A2A skill (agent → agent)<agent_id>.<skill_id>scheduler.run_routine
MCP toolmcp.<server_name>.<tool_name>mcp.whatsapp.send_message

An MCP tool checks this with one line at the top of the function — permissions.enforce_mcp_permission(ctx, 'mcp.whatsapp.send_message') — which raises PermissionDenied (turned into a normal tool-error result by the MCP SDK) if the caller's tier doesn't allow it. No token, an expired one, or a bad signature is treated exactly like an unauthenticated stranger — never a special error path.

Notice the pattern: every agent that needs to send WhatsApp gets its own tier, not a share of service. That's not incidental — see §6.

4. Adding a new tier

One JSON block in mesh/lib/permissions_config.json, under "tiers":

"my_agent_service": {
  "description": "my_agent's own outbound calls - state exactly why it needs each key.",
  "allow": [
    "mcp.whatsapp.get_own_phone",
    "mcp.whatsapp.send_message"
  ]
}
  1. Name it <agent_id>_service — the convention every tier in §3 already follows, and what AdiyanAgent (§5) assumes without being told.
  2. List only what you actually call. Least privilege isn't a policy here, it's the whole design — a tier with one extra key is a tier that can do one more thing than anyone meant it to.
  3. Never reuse service. It's shared by everything that hasn't been carved out yet — adding to it widens what every caller of that tier can do, not just yours.

5. Reaching WhatsApp as a new agent

The entire integration point is one class, from mesh/lib/agent_sdk.py:

from mesh.lib.agent_sdk import AdiyanAgent

agent = AdiyanAgent('my_agent_id')
await agent.notify_owner("some processed result")

AdiyanAgent.notify_owner() derives the tier name (my_agent_id_service), mints the token, resolves the owner's own phone via get_own_phone, builds the chat_id, and sends through the gated send_message tool — all internal. No agent ever needs to know a tier, a token, or whatsapp_mcp's URL exist. It returns False (never raises) on any failure — no phone resolved, tier not allowed, OpenWA unreachable — matching this mesh's rule that a failed notification disappears quietly rather than surfacing as an unhandled exception.

The only two things you still do by hand

  1. Add the <agent_id>_service tier block from §4 — an explicit, human-reviewed grant, never auto-created by code.
  2. Call agent.notify_owner(text) wherever your agent needs to tell the owner something.

6. The bypass pitfall — don't construct OpenWAService directly

mesh/lib/utilities/whatsapp/openwa_service.py's OpenWAService class talks straight to OpenWA's REST API using the real API key from the vault. It has no idea permissions exist — no token, no tier, no check of any kind.

Confirmed in this codebase today Three call sites construct OpenWAService directly instead of going through whatsapp_mcp: mesh/scheduler/skills/run_routine.py, mesh/adiyan_reader/skills/read_next_page.py, and mesh/adiyan_reader/skills/dispatch_questions.py. Each one can send a WhatsApp message regardless of what any tier in permissions_config.json says — the 2026-08-30 lockdown that removed send_message from service doesn't actually restrict Scheduler, because Scheduler's send call never passes through the gate that lockdown closed.

The rule going forward: the only file that should ever construct OpenWAService is mesh/mcp/whatsapp/server.py itself — that's the one place enforce_mcp_permission() runs before it's touched. Every other caller reaches WhatsApp through whatsapp_mcp's MCP tools (ideally via AdiyanAgent, §5), never around them.

7. Checklist: adding a new agent's WhatsApp capability

  1. Pick your agent's id — the same string you'd use as AGENT_ID in its constants.py.
  2. Add a <agent_id>_service tier to permissions_config.json (§4), listing only the permission keys you actually call.
  3. from mesh.lib.agent_sdk import AdiyanAgent, construct once with your agent id.
  4. Call await agent.notify_owner(text) wherever you need to reach the owner. Check the return value if you want to know whether it actually sent — don't assume.
  5. Never import or construct OpenWAService yourself (§6).
Reflects the mesh as of the AdiyanReader-tier and AdiyanAgent-SDK work — the OpenWAService bypass in §6 is a known, not-yet-fixed gap, called out here so nobody builds a fourth instance of it.
