2. Why text tokens become audio at all

The part that looks like magic: Ollama outputs plain text, but that text is the audio, encoded.

Orpheus doesn't generate audio directly - it generates text tokens that look like <custom_token_17423>. Each one is really a numeric code from SNAC (a neural audio codec), smuggled through Ollama's ordinary text-completion API as a token string. Every 7 of these tokens forms one "frame" of audio, split across 3 hierarchical codebooks:

codebook 0tok 0
codebook 1tok 1tok 4
codebook 2tok 2tok 3tok 5tok 6

That's SNAC's fixed 7-tokens-per-timestep interleaving (_convert_frame_to_audio). A local SNAC decoder model (hubertsiuzdak/snac_24khz, loaded once via torch, on whatever GPU is available) turns those 3 codebooks back into a real slice of 16-bit PCM audio - the actual waveform. Ollama never touches real audio at any point; it only ever predicts the next token, same as it does for text.

3. Where the emotion tags fit

Last night's test, explained by the pipeline above.

A tag like <laugh> is just literal text inserted into the chunk before step 4 (Orpheus prompt) - <|audio|>tara: I'm going to laugh now. <laugh>.<|eot_id|>. Orpheus was trained so that seeing this exact text in context shifts which <custom_token_N> values it predicts next - producing SNAC codes that decode to an actual laugh sound instead of the word "laugh." Nothing downstream (SNAC, the WAV writer, the Opus transcode) knows or cares that a tag was involved - it's audio like any other by the time it reaches step 5.
